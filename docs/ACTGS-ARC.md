# ACTGS（PC 版）归档格式说明

适用：`ACTGS ver 2.33`（ACTRESS，Win32 / Delphi-VCL）。
样本：WHITE CLARITY（PC 版）。对应插件 `Archives/ACTGS ARC.cs`。

结论均来自静态反编译 + 运行时实测，文末给出可复核的判据。

---

## 1. 一览

同一引擎存在**三种容器布局**，由打开归档时的一个标志位区分：

| 归档 | 索引布局 | 记录字段 | 数据块混淆 | 本插件 |
|---|---|---|---|---|
| `arc.scr` | 连续 `N×32`，紧跟 16 字节头 | `[off:4][size:4][name:24]` | 有 `'X'` 标记，块内 `key[(i-1)%5]` | ✅ |
| `arc.cg` | **记录与数据交错**，自 `0x1000` | `[size:4][name:28]`，偏移由引擎推算 | 无标记，块内 `key[i%5]` | ✅ |
| `arc.wav` | 连续 `N×24` | `[off:4][size:4][name:16]` | **无（明文）** | ❌ |

## 2. 密钥

```
KEY = 11 05 22 33 41          长度 5
```

以 NUL 结尾字符串形式明文存在于 `.data`，运行时用 `strlen` 取长，共 4 份副本：

| VA | 引用函数 | 作用对象 |
|---|---|---|
| `0x4C5460` | `FUN_00429568` | 归档索引 |
| `0x4BFEDF` | `FUN_004124d0` | 脚本数据块 |
| `0x4C2A28` | `FUN_0042629c` | PSD 资源 |
| `0x4C5857` | `FUN_0042a32c` | DIBitmap 资源 |

属**混淆**而非加密：无完整性校验、无密钥派生，明文区大量 0 填充。

## 3. 布局 A：连续索引（`arc.scr`）

```
[0x0000,0x010)   uint32 N + 12 字节 0        明文
[0x010, …)       N × 32 字节索引             key[i%5] 混淆，i 以索引区首为 0
其后             数据块，各块按 16 字节对齐
```

记录字段：`+0x00` 绝对偏移、`+0x04` 原始长度、`+0x08` 文件名（NUL 结尾，cp932）。
数据区起点 = `16 + N×32`（样本中 `N=164` → `5264`，与 `rec[0].off` 吻合）。

数据块：

```c
if (blob[0] == 'X') {                 /* 0x58 标记 */
    plain[0] = 'N';                   /* 0x4E，恒定 */
    for (i = 1; i < len; i++)
        plain[i] = blob[i] ^ KEY[(i - 1) % 5];
}
```

> ⚠ **相位陷阱**：下标是 `(i-1)%5`，不是 `i%5`。
> 引擎源码写作 `u = u % klen + 1` 的滚动形式，循环自 `i=1` 起，等价于 `(i-1)%5`。
> 写成 `i%5` 会整块错一位，症状为"块首正常、其后全乱"，极易被误判成"还有第二层加密"。

## 4. 布局 B：记录与数据交错（`arc.cg`）

引擎从 `0x1000` 起逐条遍历，**记录之间不连续**，靠记录自身的 size 字段跳转：

```
pos = 0x1000
repeat N 次:
    rec  = decrypt32(read(pos, 32))          # 逐条独立，相位从 0 起
    size = u32(rec[0:4])
    name = rec[4:32] 截 NUL
    data = decrypt_stream(read(pos+32, size)) # 整块连续，相位从 0 起
    pos += 32 + align16(size)
```

记录字段只有 `[size:4][name:28]`；**偏移不存储**，由引擎按
`off[i] = off[i-1] + align16(size[i-1]) + 32`、`off[0] = 0x1020` 推算。

> ✅ **强判据**：遍历结束时最后一条数据块的结束地址必须**精确等于文件大小**。
> 样本实测 `942,221,792 == 文件大小`。这是布局 B 最可靠的接受条件，也是与
> 其他 `.cg` 文件区分的主要依据。

## 5. 布局 C：`arc.wav`（未支持）

24 字节记录 `[off][size][name16]`，数据不混淆（如 `bgm01.wav`）。
未支持的原因：数据区起点与索引区末端之间存在一段**尚未解析的间隔**
（样本中 `16 + 5779×24 = 138712`，而首条 `off = 184944`）。

因此插件**没有注册 `wav` 扩展名**，以免把普通 wav 音频误判为容器。

## 6. 图像条目：不要写图像插件

`arc.cg` 解密后的条目本身就是标准格式（样本 1003 条）：

```
"8BPS" × 900    标准 PSD（channels / height / width / depth / mode 均为标准布局）
"BM"   × 103    标准 24bit 无压缩 BMP（bfOffBits=54, biSize=40, planes=1）
```

`UI/MainForm.Preview.cs` 的 `TryDecodeImage()` 在所有插件未命中时有 builtin 回退：

```csharp
decoded = Image.FromStream(s, true, true);   // GDI+ 原生支持 BMP / PSD
```

> ❌ **不要**为它注册 `extensions:{bmp,psd}` 或 `magics:{BM,8BPS}` 的图像插件。
> 那会插到 builtin 乃至专用插件之前，抢走其他游戏（含 WHITE CLARITY **PS2 版**的
> AFS+PB6 通路）的 `.bmp` 条目。容器插件只注册 `scr` / `cg`，不碰 `bmp`。

## 7. 脚本正文（汉化相关）

`arc.scr` 解出后是**纯文本 cp932 脚本**，行分隔 `CRLF`：

| 行首 | 语义 |
|---|---|
| `A-Z` / `a-z` | 命令行（`vo` `msg2` `ret` `bgm1` `se2` `sp1_cf` `bg1_fi` `set_all_fade` …） |
| `;` | 注释 |
| 双字节前导 | 显示正文（唯一可翻译对象） |

> 把正文改成纯 ASCII 英文会直接触发 `SCRIPT ERROR / 未定義のコマンド`，
> 因为引擎按"字母开头 = 命令名"查表。

引擎的双字节前导判定表在运行时构建于 `0x4CE218`（镜像内全 0），
其内容**跟随系统 ANSI 代码页**：ACP=936 时实测为 `0x81–0xFE` 全置位（即 GBK 前导集）。
故中文 GBK 正文在中文系统上可直接渲染，**无需内码补丁**；但该结论依赖宿主 ACP，
换到 932/1252 环境会失效。

## 8. 复核判据

| 判据 | 期望 |
|---|---|
| `arc.scr` 全明文以 cp932 解码 | **零非法字节**（样本 2,403,410 字节） |
| `arc.cg` 布局 B 遍历结束 | 末块结束 == 文件大小 |
| `arc.scr` 首条 `off` | == `16 + N×32` |
| 解包→原样回封 | 与原始文件**逐字节一致** |

> 注意"解包→回封一致"只证明**回写不丢信息**（对齐、填充、尾部、索引边角字段都在），
> **不证明**解密算法与引擎一致——任何可逆变换都能满足它。算法正确性以第 1 条判据为准。
